# نظام إدارة شبكة البرنس

نظام ويب إداري متكامل لإدارة بيع باقات الإنترنت، والمخزون بالشدات، والموزعين، والمبيعات، والتحصيلات، والخطوط، والمصروفات، والصندوق، والتقارير المالية. صُمم النظام ليكون عربيًا بالكامل، متجاوبًا مع الجوال والكمبيوتر، وسهل الاستخدام والصيانة، وقابلًا للتشغيل على استضافة مشتركة تدعم PHP وMySQL.

---

## 1. الهدف من المشروع

إنشاء نسخة جديدة ومستقلة من نظام شبكة البرنس، مع إعادة بناء النظام من الصفر باستخدام PHP وMySQL وHTML وCSS وJavaScript، مع الاحتفاظ بوظائف النظام الحالي وقواعد العمل وتصميمه البصري قدر الإمكان.

الملف المرفق `prince-net-design-reference.zip` هو المرجع الأساسي للتصميم والواجهات. يجب فحص محتوياته والاستفادة من ملفات CSS وإعدادات الألوان والخطوط ومكونات الواجهة والصفحات الأصلية لإعادة إنشاء التصميم، دون نسخ تقنيات React أو Tailwind إلى المشروع الجديد.

المطلوب ليس إنشاء واجهات شكلية فقط، بل تطبيق متكامل بقاعدة بيانات حقيقية، وعمليات مالية ومخزون مترابطة، وتحقق من البيانات على الخادم.

## 2. التقنيات الإلزامية

### Backend

- PHP 8.2 أو إصدار مستقر أحدث متوافق مع الاستضافة.
- Native PHP بأسلوب MVC،
- MySQL أو MariaDB.
- PDO والاستعلامات المحضّرة.
- جلسات PHP آمنة للمصادقة.
- معاملات قاعدة البيانات `Transactions` للعمليات المالية والمخزنية التي تتطلب اتساقًا ذريًا.

### Frontend

- HTML5.
- CSS3 عادي.
- JavaScript عادي دون أطر عمل.
- واجهة عربية كاملة باتجاه RTL.
- تصميم متجاوب يبدأ من الهاتف Mobile-First.
- استخدام SVG أو أيقونات محلية عند الحاجة، دون فرض إطار عمل للواجهة.

### الممنوع استخدامه

- React أو JSX.
- Node.js أو npm أو Vite كمتطلبات تشغيل أو بناء.
- Tailwind CSS في المشروع النهائي.
- Laravel أو أي إطار عمل PHP.
- الاعتماد على Base44 SDK أو خدمات Base44 الخلفية أو قاعدة بياناتها.
- الاعتماد على واجهات برمجية خارجية لتشغيل الوظائف الأساسية.

يجب أن يعمل المشروع مباشرة على استضافة تدعم PHP وMySQL، دون خطوات بناء للواجهة.

## 3. هيكل المشروع الإلزامي

يجب الالتزام بالهيكل التالي، وعدم إنشاء مجلدات رئيسية أخرى خارجه. يمكن إنشاء ملفات ومجلدات فرعية داخل المجلدات المحددة عند الحاجة.

```text
prince-net/
├── index.php
├── .htaccess
├── config/
│   └── database.php
├── app/
│   ├── Controllers/
│   ├── Models/
│   ├── Services/
│   └── Views/
├── assets/
│   ├── css/
│   ├── js/
│   └── images/
├── database/
│   └── schema.sql
├── tools/
└── README.md
```

### مسؤولية كل جزء

- `index.php`: نقطة الدخول الرئيسية، وتحويل الطلبات إلى المسارات المناسبة.
- `.htaccess`: إعداد المسارات النظيفة وحماية الملفات الحساسة عند دعم Apache.
- `config/database.php`: إعداد اتصال PDO بقاعدة البيانات.
- `app/Controllers/`: استقبال الطلبات وتنفيذ الإجراءات والتحقق من الصلاحيات.
- `app/Models/`: التعامل مع الجداول والاستعلامات والعلاقات.
- `app/Services/`: منطق الأعمال والحسابات المالية والمخزون والفواتير والنسخ الاحتياطي.
- `app/Views/`: الواجهات والقوالب المشتركة وصفحات النظام.
- `assets/css/`: جميع ملفات التنسيق العادية، بما فيها الثيم والمكونات والطباعة.
- `assets/js/`: التفاعلات والقوائم والنوافذ والتقويم والتحقق من النماذج.
- `assets/images/`: الشعارات والصور والأصول البصرية.
- `database/schema.sql`: إنشاء الجداول والعلاقات والفهارس والقيود.
- `tools/`: أدوات الصيانة والتشخيص والاستيراد والتصدير اللازمة، دون وضع ملفات عامة غير محمية فيه.
- `README.md`: التوثيق وتعليمات التثبيت والتشغيل.

## 4. مرجع التصميم والهوية البصرية

الملف `prince-net-design-reference.zip` هو المرجع الأساسي للشكل البصري. يجب فحص الملفات الموجودة داخله قبل البدء في تنفيذ الواجهات.

### الملفات المرجعية المهمة

- `src/index.css`: الألوان العامة، متغيرات CSS، الخطوط، RTL، الوضع الداكن، الطباعة وتأثيرات التمرير.
- `tailwind.config.js`: الألوان والخطوط والزوايا والظلال والحركات ونقاط التوقف.
- `components.json`: إعدادات مكونات الواجهة الأصلية.
- `src/components/Layout.jsx`: القائمة الجانبية والتنقل للجوال.
- `src/components/ui-shared.jsx`: البطاقات والعناوين وحالات التحميل والحالات الفارغة.
- `src/components/Modal.jsx`: النوافذ المنبثقة.
- `src/components/DatePicker.jsx`: التقويم العربي.
- `src/components/DrawerSelect.jsx`: القوائم المنسدلة المتجاوبة.
- `src/components/InvoiceModal.jsx`: تصميم الفاتورة والطباعة والمشاركة.
- `src/components/ui/`: المكونات الأصلية للأزرار والجداول والبطاقات والنوافذ وغيرها.
- `src/pages/`: صفحات النظام وتنسيقاتها المباشرة وأصناف Tailwind الخاصة بها.

هذه الملفات مرجع للتصميم والسلوك، وليست ملفات قابلة للتشغيل مباشرة داخل مشروع PHP الجديد.

### طريقة تحويل التصميم

1. استخرج الألوان والخطوط والقيم من ملفات CSS وإعدادات Tailwind الأصلية.
2. حوّل أصناف Tailwind المستخدمة فعليًا إلى قواعد CSS عادية.
3. أعد بناء المكونات باستخدام HTML وPHP وCSS وJavaScript.
4. احتفظ بأسماء متغيرات CSS واضحة وموحدة للألوان والمسافات والزوايا والظلال.
5. أنشئ مكونات مشتركة قابلة لإعادة الاستخدام داخل `app/Views/`.
6. اختبر الشكل على الهاتف والكمبيوتر، وقارن النتيجة بالمرجع الأصلي.
7. لا تكتفِ بتقليد الألوان؛ انقل التباعد والأحجام والمحاذاة والحالات التفاعلية وسلوك القوائم والنوافذ.

### الهوية المطلوبة

- الخلفية الكحلية والقائمة الجانبية حسب المرجع الأصلي.
- البطاقات البيضاء أو ألوان الأسطح المستخدمة في التصميم الأصلي.
- خط Cairo واتجاه RTL.
- الألوان الأصلية للحالات والأزرار والتنبيهات.
- الحواف الدائرية والظلال والمسافات الأصلية.
- الوضع الداكن إذا كان موجودًا في المرجع.
- تصميم متجاوب لا يسبب تجاوزًا أفقيًا على الشاشات الصغيرة.
- الحفاظ على المظهر العام على الكمبيوتر والجوال.
- واجهات متناسقة لجميع صفحات النظام.

يجب استخدام CSS عادي في المشروع النهائي، دون استيراد Tailwind أو تشغيل React.

## 5. اللغة وتجربة الاستخدام

- جميع الواجهات باللغة العربية.
- اتجاه الصفحة `RTL`.
- استخدام مصطلحات النظام مثل: الباقات، الشدات، الموزعون، المبيعات، التحصيلات، الخطوط، المصروفات، الصندوق.
- عرض العملة بالريال اليمني `ر.ي` افتراضيًا.
- عرض مبالغ الأسعار الأساسية كأعداد صحيحة دون منازل عشرية غير ضرورية.
- استخدام تنسيق موحد للتواريخ والمبالغ والأرقام.
- رسائل نجاح وفشل واضحة باللغة العربية.
- حالات تحميل واضحة عند جلب البيانات.
- حالات فارغة منظمة عندما لا توجد سجلات.
- تأكيد العمليات الحساسة، مثل الإلغاء والحذف والاستعادة.
- منع تكرار إرسال النموذج عند تنفيذ العملية.
- دعم لوحة المفاتيح وأحجام لمس مناسبة للجوال.
- عدم استخدام بيانات ثابتة بدل بيانات قاعدة البيانات.

## 6. تسجيل الدخول والصلاحيات

يحتوي النظام على حساب مدير واحد في الاستخدام الأساسي.

المتطلبات:

- تسجيل الدخول بالبريد أو اسم المستخدم وكلمة المرور وفق تصميم مناسب.
- حفظ كلمات المرور باستخدام `password_hash()` والتحقق باستخدام `password_verify()`.
- تخزين حالة الدخول في جلسات PHP آمنة.
- تجديد معرّف الجلسة بعد تسجيل الدخول.
- حماية جميع الصفحات والإجراءات الإدارية.
- تسجيل الخروج وإبطال الجلسة.
- حماية CSRF للنماذج والطلبات التي تغيّر البيانات.
- التحقق من الصلاحيات داخل الخادم، وليس إخفاء الأزرار فقط.
- منع إنشاء حسابات عامة غير مصرح بها.
- توفير طريقة آمنة لإعداد كلمة مرور المدير الأولى.
- عدم تخزين كلمات المرور أو الأسرار في المستودع أو ملفات الواجهة.

لا تُنشئ بيانات دخول افتراضية ثابتة أو كلمة مرور معروفة للجميع.

## 7. الوحدات الأساسية

### 7.1 لوحة التحكم

تعرض معلومات حقيقية مستخرجة من قاعدة البيانات:

- إجمالي المبيعات اليومية والشهرية.
- المبالغ النقدية والآجلة.
- رصيد الصندوق الحالي.
- إجمالي الديون المستحقة على الموزعين.
- إجمالي التحصيلات.
- المصروفات وسحوبات المالك ودفعات الخطوط.
- قيمة المخزون الحالي.
- تنبيهات انخفاض المخزون.
- أحدث العمليات.
- روابط سريعة إلى الوظائف الأساسية.

يجب أن تعتمد الإحصائيات على البيانات الفعلية، وألا تستخدم أرقامًا ثابتة.

### 7.2 إدارة الباقات

تتيح إضافة الباقات وتعديلها وتفعيلها وتعطيلها.

الحقول الأساسية:

- اسم الباقة أو رمزها.
- سعر الباقة الأساسي.
- حجم البيانات بالميغابايت.
- عدد الساعات.
- اللون.
- الحالة.
- الوصف عند الحاجة.

يجب أن تدعم الواجهة الباقات الحالية مثل 100 و200 و250 و500 و1000، مع الاحتفاظ بقيم البيانات والساعات المحددة لكل باقة في النظام الأصلي.

سعر الباقة الأساسي وسعر بيع الشدة  نفس السعر في قواعد العمل. سعر الحقل `price` هو سعر الشدة دون مراجعة التوثيق المرجعي.

لا يؤدي تعطيل الباقة إلى حذف تاريخ مبيعاتها أو حركات مخزونها.

### 7.3 إدارة المخزون

المخزون يُدار بالشدات، وليس بعدد البطاقات الفردية.

الوظائف:

- عرض المخزون المتبقي لكل باقة.
- إضافة كمية جديدة بالشدات.
- تسجيل تكلفة الشدة أو سعر التكلفة المعتمد لكل إضافة.
- عرض سجل حركات المخزون.
- التسوية بالزيادة أو النقصان مع تسجيل السبب.
- عرض إجمالي المضاف والمباع والمرتجع والتسويات.
- حساب قيمة المخزون من بيانات التكلفة الفعلية.
- إظهار تنبيهات انخفاض المخزون.
- الاحتفاظ بتاريخ الحركات وعدم تعديل التاريخ المالي بصمت.

تُحفظ تكلفة كل إضافة وقت إنشائها، حتى لا تتغير تكلفة الحركات القديمة عند تغيير الأسعار لاحقًا.

يجب رفض الكميات السالبة أو الصفرية أو الكسرية عندما تكون 1 شدة كاملة.

### 7.4 إدارة الموزعين

تتضمن:

- إضافة موزع وتعديل بياناته.
- الاسم ورقم الهاتف والعنوان والملاحظات والحالة.
- البحث عن الموزع.
- عرض المبيعات والفواتير والتحصيلات المرتبطة به.
- عرض الرصيد المستحق.
- عرض سجل العمليات.
- منع حذف موزع لديه سجلات مالية مترابطة إلا من خلال سياسة آمنة تحافظ على التاريخ.

### 7.5 المبيعات والفواتير

تتضمن:

- اختيار الموزع.
- إضافة باقة أو أكثر إلى الفاتورة.
- إدخال عدد الشدات لكل عنصر.
- حساب الإجمالي على الخادم.
- تحديد نوع البيع: نقدي أو آجل.
- إصدار رقم فاتورة فريد.
- تسجيل تاريخ البيع.
- عرض تفاصيل الفاتورة.
- طباعة الفاتورة ومشاركتها عبر واتساب.
- البحث والتصفية حسب التاريخ والموزع ورقم الفاتورة والحالة.
- إلغاء الفاتورة وفق قواعد مالية واضحة.

يجب أن تأتي أسعار البيع المعتمدة من قاعدة البيانات والخادم، وليس من القيم التي يرسلها المتصفح.

يجب تجميع كميات الباقة نفسها داخل الفاتورة قبل التحقق من المخزون، لمنع تجاوز الكمية المتاحة عند تكرار الباقة في عدة أسطر.

تُنفذ عملية البيع وحركات المخزون وحركة الصندوق ضمن معاملة قاعدة بيانات مناسبة. عند الفشل يجب ألا تبقى فاتورة أو حركة مالية أو مخزنية ناقصة.

### 7.6 التحصيلات

تتضمن:

- تسجيل تحصيل من موزع.
- تحديد الموزع.
- ربط التحصيل بفاتورة محددة عند الحاجة.
- تسجيل المبلغ والتاريخ والملاحظات.
- التحقق من الدين المستحق قبل قبول التحصيل.
- السماح بالتحصيل الجزئي ضمن المبلغ المستحق.
- تحديث الرصيد المحسوب للموزع.
- تسجيل حركة نقدية داخلة للصندوق.

عند ربط التحصيل بفاتورة، يجب أن تكون الفاتورة موجودة ونشطة وتتبع الموزع نفسه، وأن يكون المبلغ ضمن المتبقي المستحق.

يجب منع التحصيلات غير الصحيحة وعدم السماح بإعادة تحصيل مبلغ سبق تسويته.

### 7.7 تفاصيل الموزع

تعرض صفحة مستقلة لكل موزع:

- البيانات الأساسية.
- إجمالي المبيعات النشطة.
- إجمالي المبالغ المدفوعة عند البيع.
- إجمالي التحصيلات الصالحة.
- الرصيد المتبقي.
- سجل الفواتير.
- سجل التحصيلات.
- حالة الفواتير والتحصيلات الملغاة أو المعكوسة.

يجب أن يتطابق الرصيد مع منطق الحسابات المالية، وأن تكون السجلات الملغاة واضحة للمستخدم.

### 7.8 إدارة خطوط الإنترنت

تتيح:

- إضافة خط وتعديله وتعطيله.
- اسم الخط ومزود الخدمة والمعرّف والسرعة.
- تكلفة الاشتراك.
- تاريخ الاشتراك.
- الحالة والملاحظات.
- عرض تفاصيل الخط ودفعاته.

### 7.9 دفعات الخطوط

تتضمن:

- اختيار الخط.
- اختيار - تكلفة الاشتراك.
- اختيار تاريخ التسديد.
- تسجيل الملاحظات.
- خصم المبلغ من الصندوق وفق القواعد المعتمدة.
- عرض سجل الدفعات.
- تصفية الدفعات حسب التاريخ والخط.

يجب حفظ التاريخ الذي يختاره المستخدم كتاريخ التسديد الفعلي في السجل وحركة الصندوق، مع معالجة السجلات القديمة التي قد تحتوي على حقول تاريخ مختلفة.

### 7.10 المصروفات

تتضمن:

- تسجيل المصروف.
- المبلغ والتصنيف والوصف والتاريخ والملاحظات.
- تصنيفات مناسبة مثل الإنترنت والكهرباء والصيانة والرواتب وغيرها.
- تسجيل حركة نقدية خارجة.
- البحث والتصفية حسب التاريخ والتصنيف.
- عرض الإجماليات حسب الفترة.

### 7.11 سحوبات المالك

تتضمن:

- تسجيل مبلغ السحب.
- السبب والملاحظات والتاريخ.
- تسجيل حركة نقدية خارجة.
- التحقق من رصيد الصندوق وفق السياسة المعتمدة.
- عرض السجل والإجماليات.

### 7.12 الصندوق

يحتوي على سجل موحد لحركات النقد:

- المقبوضات.
- المدفوعات.
- المبيعات النقدية.
- التحصيلات.
- المصروفات.
- دفعات الخطوط.
- سحوبات المالك.
- حركات العكس الناتجة عن إلغاء العمليات.
- الرصيد الافتتاحي.

يُحسب الرصيد من الحركات الفعلية:

الرصيد الحالي = الرصيد الافتتاحي + إجمالي المقبوضات − إجمالي المدفوعات.

يجب ربط كل حركة بالعملية التي أنشأتها، ومنع احتساب الحركة نفسها أكثر من مرة.

لا يسمح النظام بإنشاء حركة نقدية مكررة عند إعادة إرسال الطلب، ويجب معالجة العمليات المتزامنة بطريقة تمنع تجاوز الرصيد أو تكرار الصرف.

### 7.13 التقارير

تتضمن:

- تقارير المبيعات.
- تقارير التحصيلات.
- تقارير الديون.
- تقارير المصروفات.
- تقارير دفعات الخطوط.
- تقارير سحوبات المالك.
- تقارير حركات الصندوق.
- تقارير المخزون وقيمته.
- تقارير يومية وشهرية وفترة مخصصة.
- التصفية حسب التاريخ والموزع والباقة والحالة.
- عرض الإجماليات والنتائج التفصيلية.
- الطباعة والتصدير عند الحاجة.

يجب حساب التدفق النقدي من حركات الصندوق الفعلية وتواريخها، بما فيها الحركات العكسية الناتجة عن الإلغاء. لا تخلط بين إجمالي المبيعات والتدفق النقدي، ولا تحتسب حركات العكس مرتين.

يجب ألا تُفقد السجلات عند تجاوز عدد كبير من النتائج؛ استخدم ترقيم الصفحات والاستعلامات المناسبة، مع حساب الإجماليات من جميع السجلات المطابقة للفترة وليس من الصفحة المعروضة فقط.

### 7.14 البحث الشامل

يتيح البحث عن:

- الباقات.
- الموزعين.
- الفواتير.
- التحصيلات.
- المصروفات.
- الخطوط ودفعاتها.
- حركات الصندوق.

يجب احترام صلاحيات المستخدم، وعرض النتائج بوضوح مع روابط للصفحات المناسبة.

### 7.15 سجل التدقيق

يسجل العمليات الإدارية المهمة:

- إنشاء السجلات وتعديلها.
- عمليات البيع والإلغاء.
- التحصيلات.
- تعديلات المخزون والتسويات.
- المصروفات والسحوبات.
- تغييرات الإعدادات.
- النسخ الاحتياطي والاستعادة.

يشمل السجل نوع العملية، والسجل المتأثر، والتاريخ، والتفاصيل، ويجب ألا يسمح للمستخدم العادي بتعديل سجل التدقيق أو حذفه من الواجهة.

### 7.16 الإعدادات

تتضمن:

- اسم الشبكة.
- العملة ورمزها.
- إعدادات المدير.
- الرصيد الافتتاحي للصندوق.
- حد تنبيه المخزون.
- الإعدادات العامة اللازمة لتشغيل النظام.

تُطبق التغييرات على الواجهات والحسابات المناسبة، مع التحقق من صلاحية القيم.

### 7.17 النسخ الاحتياطي والاستعادة

- تصدير نسخة احتياطية من بيانات النظام إلى ملف مناسب.
- حماية النسخ الاحتياطية من الوصول العام.
- التحقق من سلامة الملف قبل الاستعادة.
- طلب تأكيد واضح قبل الاستعادة.
- استخدام معاملة أو آلية آمنة كلما أمكن.
- عدم حذف البيانات الحالية قبل التأكد من صلاحية النسخة وإمكانية استعادتها.
- تسجيل عمليات النسخ الاحتياطي والاستعادة في سجل التدقيق.

## 8. قواعد العمل المالية والمخزنية

هذه القواعد إلزامية:

1. لا يوجد قسم للموردين أو المورّدين في النظام.
2. بيع الشدات هو وحدة المخزون الأساسية.
3. أسعار البيع والتكاليف تُحفظ بالقيم الصحيحة وقت العملية.
4. تُحسب أرصدة الموزعين من المبيعات والتحصيلات الصالحة.
5. لا تُحسب التحصيلات المرتبطة بفواتير ملغاة ضمن الدين الصالح إذا تم عكسها وفق قواعد الإلغاء.
6. لا يُسمح ببيع كمية تتجاوز المخزون.
7. لا تُقبل كميات شدات كسرية.
8. تُحسب قيمة المخزون من حركاته وتكاليفه التاريخية وفق سياسة واضحة.
9. لا يؤدي تغيير سعر الباقة إلى تعديل أسعار الفواتير القديمة.
10. لا تُحذف السجلات المالية التاريخية عند إلغاء العمليات؛ تستخدم حالة الإلغاء وحركات العكس المناسبة.
11. لا يتم إنشاء حركة صندوق مستقلة مكررة للعملية نفسها.
12. لا يُقبل أي مبلغ أو سعر أو إجمالي نهائي من الواجهة دون التحقق منه في الخادم.
13. جميع العمليات المالية المترابطة يجب أن تكون متسقة عند النجاح أو الفشل.
14. يجب معالجة إعادة إرسال الطلبات وتعارض العمليات المتزامنة.
15. لا تُستخدم أرقام ثابتة أو بيانات وهمية في لوحة التحكم أو التقارير بعد تشغيل النظام.

## 9. تصميم قاعدة البيانات

أنشئ قاعدة بيانات MySQL مترابطة، مع مفاتيح أساسية وأجنبية وفهارس وقيود مناسبة.

الجداول الأساسية المقترحة:

- `users`
- `packages`
- `inventory_movements`
- `distributors`
- `sales`
- `sale_items`
- `collections`
- `lines`
- `line_payments`
- `expenses`
- `owner_withdrawals`
- `cash_transactions`
- `settings`
- `audit_logs`
- `backups`

يمكن إضافة جداول داخل قاعدة البيانات نفسها عند وجود ضرورة واضحة.

يجب استخدام أنواع رقمية دقيقة للمبالغ المالية، وعدم الاعتماد على أعداد الفاصلة العائمة في الحسابات المالية.

يجب أن تتضمن الجداول حقول التواريخ والحالة والمراجع اللازمة لحفظ التاريخ المالي وربط العمليات.

لا تخزّن الرصيد المحسوب أو المبلغ المدفوع أو المتبقي كقيم مستقلة قابلة للتعارض مع السجلات الأصلية؛ احسبها من الحركات المرتبطة، أو استخدم آلية تحديث موثوقة ومضبوطة عند وجود ضرورة تقنية مثبتة.

## 10. الأمان والموثوقية

- استخدام PDO مع الاستعلامات المحضّرة.
- حماية CSRF.
- ترميز المخرجات لمنع XSS.
- التحقق من كل مدخل في الخادم.
- استخدام الجلسات الآمنة.
- حماية الملفات الحساسة من الوصول المباشر.
- منع الوصول إلى الصفحات الإدارية دون تسجيل الدخول.
- تطبيق صلاحيات الإدارة على كل إجراء.
- منع SQL Injection.
- استخدام معاملات قاعدة البيانات للعمليات المترابطة.
- منع تكرار العمليات الحساسة.
- حماية النسخ الاحتياطية وبيانات الاتصال.
- تسجيل الأخطاء في سجلات داخلية دون عرض تفاصيل حساسة للمستخدم.
- عدم كشف كلمات المرور أو أسرار الاتصال أو تفاصيل الأخطاء الداخلية.
- الحفاظ على سلامة السجلات التاريخية.

## 13. شروط القبول النهائي

- جميع الوظائف الأساسية تعمل.
- التصميم قريب قدر الإمكان من مرجع شبكة البرنس.
- لا توجد صفحات شكلية أو أزرار غير عاملة.
- قاعدة البيانات حقيقية ومترابطة.
- الحسابات المالية متطابقة مع الحركات.
- المخزون لا يتجاوز الكميات المتاحة.
- لا توجد أخطاء معروفة في العمليات المترابطة دون معالجة.
- الواجهة تعمل على الجوال والكمبيوتر.
- المشروع لا يحتاج إلى React أو Node.js أو Tailwind أو Laravel.
- يمكن تثبيته على استضافة PHP وMySQL باستخدام تعليمات README.
- لا تُدّعى نجاحات اختبار لم يتم تنفيذها فعليًا.

## 14. تعليمات أخيرة للمطور أو أداة البرمجة

ابدأ بفحص الملفات المرجعية قبل كتابة الكود. لا تفترض أن اسم ملف أو لونًا أو قيمة غير موجودة في المصدر صحيحة؛ استخرج القيم من الملفات الأصلية.

التصميم المطلوب هو إعادة بناء التصميم الحالي باستخدام CSS وHTML وJavaScript حافظ على تجربة الاستخدام والمظهر العام والمكونات والسلوكيات قدر الإمكان.

التزم بالتقنيات والهيكل المحددين. لا تنشئ مجلدات رئيسية إضافية، ولا تضف موردين، ولا تغيّر قواعد العمل المالية دون مبرر واضح.

نفّذ المشروع على مراحل، واختبر كل وحدة قبل الانتقال إلى التالية. إذا كانت هناك معلومة ضرورية غير موجودة في الملفات المرجعية، وثّقها بوضوح ولا تخترع قاعدة عمل مالية من تلقاء نفسك.

**النتيجة النهائية المطلوبة:** مشروع Prince Network متكامل ومستقل باستخدام Native PHP + MVC وMySQL وHTML وCSS وJavaScript، جاهز للتثبيت على استضافة تقليدية، مع تصميم مستوحى مباشرة من الملفات الأصلية المرفقة ووظائف مالية ومخزنية متكاملة.
